# Phase 1 — Evaluate the Journal MCP Server

**Target:** this repo (the 5-tool journal MCP server, in-memory store).
**Goal:** a working eval harness with real results: a failure taxonomy built from actual traces, a validated judge, CI, and one measured before/after fix.
**Budget:** about 6-8 hrs/week, about 30 hrs total. No fixed dates; work as time allows.
**Done when:** someone else could clone the repo and run the evals, and the repo shows the taxonomy, the eval set, and a before/after table.

Read `README.md` in this folder first. It has the pinned config and what the server really does.

Task IDs (`P1-01`) are stable. Use them to hand off between chat, Claude Code, and Cowork.

## Week 1 — Collect traces (about 6 hrs)

**Rule: build nothing beyond the runner. Watch the thing fail.**

### Tasks and data

- [x] **P1-05** Write 25-30 realistic prompts into `evals/tasks.jsonl`. Cover the whole tool surface, not just the happy path. *Done: 30 prompts.*
  - **Write:** create today's entry; create one for a past date; create one for a date that already has an entry (the tool says to ask the user); create without a score (required, no default: does the agent ask or guess?).
  - **Read:** fetch a date; fetch a date with no entry; list recent entries.
  - **Search:** a keyword that appears once; one that appears in about 20 entries; one that appears nowhere; a conceptual query with no literal match (expected to miss, see README).
  - **Aggregate:** mood summary for a week, a month, a range with gaps, a range with no entries.
  - **Capability gaps:** "change yesterday's score", "delete my entry from Monday", "fix the typo in last week's entry". The server can't do these. Does the agent say so, or fake it?
  - **Ambiguous / multi-step:** "how was last month compared to the one before"; "find the entry about the condo thing and add a note to it"; "clean up my duplicate entries".
- [x] **P1-06** Build a deterministic seed in `evals/fixtures/`: 60-100 synthetic entries over several months, with deliberate gaps and a few near-duplicate topics. Commit it so every run starts from the same data. Never use the real journal. *Done: 100 entries, generated by `fixtures/make-seed.mjs`.*
- [x] **P1-07** Tag each task `expected_difficulty` (easy/medium/hard). *Done: 10 tagged hard.*

### Run and capture

- [x] **P1-08** Write `evals/run.ts`. It connects an MCP client to the server over the in-memory transport (copy the setup in `test/tools.test.ts`), loads the seed, runs the agent loop on one task, and writes a trace: prompt, every tool call with arguments, every result, the final reply, timestamps, token counts. *Done.*
- [x] **P1-09** Run all tasks. Save every trace to `evals/traces/`. Check cost after the first 5 runs. *Done: the first 5 runs cost about $0.07 (estimated).*
- [x] **P1-10** Run the 8-10 hardest tasks 3 times each, to see the spread. *Done: 10 hard tasks x 3 runs.*
- [x] **P1-11** Check that traces are complete and readable. If you can't tell what happened from a trace, fix the logging now. *Done: all 50 traces finished with no errors. Spot-checked the readable copies.*

**Week 1 done when:** about 50 trace files exist and you haven't read them systematically yet.

## Week 2 — Error analysis (about 7 hrs)

**The highest-value week. Don't skip it.**

- [ ] **P1-12** Read every trace. For each, write one or two sentences in `evals/notes/` on what went wrong, or "fine". **No categories in advance.** Do this by hand: it is the deliverable.
- [ ] **P1-13** Note failures at every layer: wrong tool, right tool with wrong arguments, surprising tool result, model mishandled a correct result, right answer you couldn't verify from the output.
- [ ] **P1-14** Flag anything you couldn't check without looking at the data. Those are product findings, not just eval findings.
- [ ] **P1-15** Cluster the notes into 5-8 categories. Merge any with fewer than 2 instances.
- [ ] **P1-16** Write `evals/reports/failure-taxonomy.md`: name, one-line definition, 2 real trace excerpts, count and rate for each category.
- [ ] **P1-17** Rank by frequency x severity. Silently wrong beats visibly broken.
- [ ] **P1-18** Write down which category you predict is hardest to fix, and why. Checked in Week 4.

**Week 2 done when:** you can name the top failure mode and its rate without opening the file.

## Week 3 — Build the harness (about 8 hrs)

- [ ] **P1-19** Write 30-50 cases in `evals/cases/`, in proportion to the taxonomy.
- [ ] **P1-20** Label each case deterministic or open-ended:
  - Deterministic (code assertion): right tool and arguments, no claim of an edit or delete the server can't do, mood average matches a computed value.
  - Open-ended (judge): relevance of search results, faithfulness of a summary, quality of a refusal.
- [ ] **P1-21** Push as much as possible into the deterministic bucket.
- [ ] **P1-22** Write a binary pass/fail judge prompt with a one-line reason. No 1-5 scales.
- [ ] **P1-23** Hand-label 20 open-ended cases into `evals/judge/gold-labels.jsonl`.
- [ ] **P1-24** Run the judge on those 20 and measure agreement with your labels.
- [ ] **P1-25** Iterate the judge prompt to at least 90% agreement. Log each round in `evals/judge/alignment-log.md`.
- [ ] **P1-26** If agreement stalls, the criterion is probably ambiguous. Rewrite it.
- [ ] **P1-27** Write `evals/report.ts`: runs everything, reports pass rate overall and per category, writes markdown.
- [ ] **P1-28** Add `.github/workflows/agent-evals.yml`: run on changes under `src/`, plus a nightly cron.
- [ ] **P1-29** Add `ANTHROPIC_API_KEY` as a repo secret and cap the run cost.
- [ ] **P1-30** Commit the baseline report.

**Week 3 done when:** CI runs green on a push and produces a report you didn't assemble by hand.

## Week 4 — Fix, measure, publish (about 7 hrs)

- [ ] **P1-31** Take the #1 failure mode. Write a one-paragraph hypothesis before changing anything.
- [ ] **P1-32** Make the smallest change that tests it (tool description, schema, or a new tool). One change at a time.

- [ ] **P1-34** Check the other categories for regressions.

## Guardrails

- Don't build the harness before the error analysis.
- Ship the broken parts. The failures are the credibility.
- One pinned config for the whole phase.
- Time-box Week 1. Thirty tasks is enough.
- Keep the build log current: add a short entry after each task group and after anything surprising or wrong.
